Problem Solving Guide

A practical method for breaking complex technical problems into clear steps, testing hypotheses and explaining solutions.

1. Restate the problem precisely

Before writing code or calculating, restate the task in your own words. Identify the required output, input format, constraints and edge cases. Separate what is known from what is assumed. If a requirement is ambiguous, ask a focused clarification rather than silently guessing.

2. Decompose the work

Break a large problem into smaller subproblems with clear inputs and outputs. For a data task, this might mean loading data, validating records, transforming values, aggregating results and presenting the answer. Solve and test each stage independently before combining them.

Example: find the most active learner

  1. Define “active” (for example, number of completed lessons in a period).
  2. Filter records to the required period.
  3. Group records by learner.
  4. Count completed lessons per learner.
  5. Sort by count and define how ties are handled.

3. Form and test hypotheses

When debugging, write down the expected behaviour and the observed behaviour. Propose one likely cause at a time, then design the smallest test that can confirm or reject it. Change one variable at a time where practical. This prevents unrelated changes from hiding the real cause.

4. Consider edge cases

Common edge cases include empty input, one item, duplicate values, missing fields, invalid formats, boundary values, unexpected ordering, time-zone differences and partial network failure. The relevant edge cases depend on the problem; do not add complexity without a reason, but do not ignore obvious boundaries.

5. Check correctness and complexity

Test the solution with a small example whose answer you can calculate manually. Then test boundary cases and a larger input. For algorithms, consider time and space complexity. For database queries, inspect row counts, joins, null handling and indexes. For user interfaces, test keyboard navigation, narrow screens and loading or error states.

6. Communicate the solution

A strong explanation states the approach, why it works, its limitations and the tests performed. Include enough detail for another person to reproduce the reasoning. If you have not tested a case, say so rather than implying complete verification.

Practice exercise

Given a list of transaction records, design a method to calculate total spend per customer for a selected month. Define how to handle refunds, duplicate transaction IDs, missing dates and customers with no transactions. Write test cases before implementing the method.

Study note: use this guide as a starting point, test the ideas with your own examples, and consult authoritative textbooks or documentation for deeper study.
